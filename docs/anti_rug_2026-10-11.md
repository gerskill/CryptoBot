## anti_rug

Fork exact du témoin (copie de `config/params.json` au 11/10 18:55 : mêmes filtres,
seuil alpha 55, sorties) + porte `src/core/anti_rug.py`, placée comme score v2
(après le seuil alpha, avant consensus/pre_trade). Lit l'instantané on-chain
calculé AVANT la décision (`OnchainObserver.snapshot`), sans aucun appel réseau.

| Paramètre (`entry_rules.`) | Valeur | Justification |
|---|---|---|
| anti_rug_require_authorities_revoked | true | Standard (mint = inflation, freeze = honeypot). Repli sur RugCheck/GMGN si l'on-chain manque. 100 % révoquées dans l'échantillon. |
| anti_rug_max_top10_wallets_pct | 20 | Nouveau champ `onchain_top10_wallets_pct` : top 10 des WALLETS hors comptes détenus par un programme (pool AMM, courbe pump.fun, lockers) et hors burn. Proxy historique (top10 − top1) : p50 17 %, p75 19,6 % → on rejette le pire quartile. |
| anti_rug_max_creator_pct | 5 | Heuristique standard (créateur > 5 % = risque de dump). Max observé 4,1 % : rarement déclenché. |
| anti_rug_max_dev_out_transfers | 5 | « Le dev a vendu » appliqué strictement refuserait **94 %** des tokens (551/589 : sur pump.fun le créateur vend presque toujours). On refuse le pire quartile de l'activité sortante du dev (p75 = 5, p90 = 57 : ventes en série / distribution vers des wallets relais). |
| anti_rug_reject_any_dev_sale | false | Variante stricte disponible, désactivée (voir ligne précédente). |
| anti_rug_max_launch_slot_buyers | 4 | Acheteurs distincts dans le slot de création (préféré à `bundle_buy_pct`, gonflé par les bots MEV). ≥ 5 = bundle classique ; p75 = 4. |
| anti_rug_max_fresh_top10 | 1 | ≥ 2 wallets frais (< 72 h) dans le top 10 = sybil. 80 % des tokens à 0. |
| anti_rug_max_fresh_first_buyers | 1 | Idem parmi les 10 premiers acheteurs (91 % à 0). |
| anti_rug_max_data_age_sec | 3600 | Instantané plus vieux = considéré manquant. |

Distribution : 168 instantanés distincts (tokens pris par un bras) du 10/10 15:42 au
11/10 18:50. Avec ces seuils (proxy top10), ~46 % auraient été refusés, hors
données manquantes. **Aucun seuil n'a été choisi sur le P&L** des trades.

Données manquantes (calcul async pas fini, budget Helius, erreur) : pas d'entrée,
`continue` → le token est réévalué aux cycles suivants tant qu'il reste candidat ;
un token jamais demandé est mis en file (non bloquant). Chaque verdict est écrit
dans `data/funnel_log.jsonl` (porte `anti_rug`, champ `missing`, détail `checks`).
